A Claude Code plugin · v0.4.2 · MIT

Nobody tests what a user actually does in a browser.

Your team writes backend tests. tddbanking closes the gap that leaves — and keeps it closed. Point it at a web app and it finds the user-facing behaviour nothing covers, writes browser tests for all of it, runs them, and hands whatever is broken to your spec tool as ready-to-implement change proposals.

Then you run it again next month, and it finds what your new features left untested.

Install How it works
/plugin marketplace add DeepSpringAI/tddbanking

The cycle

Five turns. Each one ends deliberately.

So you can look at the result before the next begins. It ends at turn 5, with the bugs it found already fixed — and a new round happens when you ask for one.

What should a user be able to do — and what covers it today?

It reads your existing test suites first, so it looks for what is untested rather than what is merely unbanked. Then it hunts three ways at once, checks each candidate is actually reachable — that a test could really set it up — and banks what it finds.

Every scenario cites evidence: a route, a commit SHA, a file:line. No evidence, no scenario.

@capability:transfers

  Scenario: Submitting a transfer twice

    When I submit a 50 EUR transfer twice
    Then only one transfer is recorded

A banked draft. No steps yet — but the intent is on the record.

Write browser tests for everything that has none.

Page Objects and step definitions for everything reachable — one capability per agent, in parallel. Not a prioritised subset: the whole list. This is the step teams skip, and skipping it is how a test suite ends up 12% done and abandoned.

Drafts and live tests share one .feature file, so it reads as the complete intent of a capability with the untested parts visibly marked.

Run them all. Give every failure a verdict.

Defect, flake, or stale scenario — each with a citation. A red browser test means three unrelated things, and “probably flaky, re-run it” is how suites die.

What it never does is edit an assertion to match what the app currently does. That converts a discovered defect into permanent blindness.

Every proven defect leaves as a change proposal.

Grouped by cause and filed into OpenSpec as a proposal, delta specs and a task-by-task plan — each one shipping its failing scenario as the acceptance test. It invokes OpenSpec to produce them, rather than writing the artifacts by hand.

Proven bugs stay tagged @known-defect so they don't block unrelated work — while the full run keeps them visible.

OpenSpec change fix-disclosure-consent
  • ✓ proposal.md
  • ✓ specs/disclosure/spec.md (delta)
  • ✓ tasks.md — 6 tasks
  • ✓ acceptance: the failing scenario

Every proposal arrives carrying its own failing test.

Take every change to green — and this is the point of all of it.

Each proposal carries a failing browser scenario, so the red half of red-green is already written, evidenced and agreed. Turn 5 invokes the tdd skill and works each change to green without touching the assertion. When a scenario passes, its @known-defect tag comes off: the bank said what was broken, and now says it is fixed.

This is the only turn that writes application code, so it confirms scope with you first and works in an isolated worktree per change.

Discovery

Three ways it finds what you're missing.

They run in parallel, each blind to the others — which is why the union is bigger than any of them. In the first real run, 88% of scenarios came from exactly one mode.

App crawl

Drives your running app: every route, form, control, error state and permission boundary. Finds what nobody wrote down.

This is the one that catches the app misbehaving in front of you.

Story-driven

Reads your README, PRDs, release notes, business rules and handoff docs, extracts what they promise, then checks each promise against the code.

Finds features that were documented, agreed, and never actually built.

Defect-driven

Mines your git history and issue tracker for bugs you already fixed and turns each into a regression test.

The most scenarios, the fewest new findings — this is insurance, not detection.

Results

What it found the first time we ran it.

On a real pharma congress platform with an existing Playwright suite of 59 tests and full backend coverage.

12% → 90%
Coverage, in one cycle — 52 of 58 scenarios live
52 pass · 6 fail
Full run, 6.4 minutes
6 defects
Real, filed as 6 OpenSpec changes

The defects were not edge cases:

A doctor who declined disclosure consent was published by name.

The system classified her correctly as an aggregate disclosure — and the report printed her name next to her transfer of value anyway. Every non-consented HCP in every report, in a product whose entire purpose is regulatory disclosure.

A Compliance Officer could cancel approved nominations and create new ones.

Role checks gated pages; nothing gated actions, so the endpoints accepted anyone.

A documented approval gate did not exist.

Four documents promised bookings were only invitation-ready once registration, hotel and flight were confirmed. The code checked one unrelated flag — and the component statuses had no update path at all, so they could never be confirmed. Story-driven mode found this by reading the docs; no crawl could have.

It also found six scenarios that cannot be tested because the fixtures don't exist, and filed those as work too — including that every seeded congress had a nomination deadline in the past, so a demo of the product's core action would have failed.

Cost

It is not cheap, and it is front-loaded.

The honest answer, measured from the run above rather than estimated. The expensive part is building the bank, and you only do that once.

~861 tokens
Added to every session, whether you use it or not — the plugin's whole descriptive surface. Installing it does not tax your normal work.
~1.95M tokens
One full cycle on a 58-scenario bank — roughly 34k per scenario banked, implemented and verified
2.1 ×
The measured speedup from parallelism — not the 12× twelve agents imply. A turn is a chain of dependent stages, so speedup is bounded by depth, not fan-out

About 2.2M if you delegate triage for all six failures — and it bought 52 working browser tests and 6 real defects on an app that already had a passing test suite. Wall clock is far less than the sum, but not by as much as the agent count suggests: adding agents within a stage buys throughput, not latency.

A second run, on a codebase ~3× larger

1.51Mtokens · 12 agents · 784 tool calls, turn 1 alone
~70 minwall clock, at that 2.1× speedup
176 / 15scenarios produced, and defects found — 3 of them severe

Roughly 100k tokens per defect found, which is the number most worth carrying into a budgeting conversation. It scaled: 3× the codebase produced 3× the scenarios and 2.5× the defects.

It also measured two things worth knowing before you spend. The evidence rule dropped 51% of candidates, every drop justified — it is not a rubber stamp. And deduplication against the existing suite dropped 35 more as already covered, which is the difference between finding what is untested and finding what is merely unbanked.

Where the money goes

Turn 2 is over half of it. Writing Page Objects and step definitions means reading real components and driving a real browser, repeatedly. The two priciest implementers — 250k and 219k — had the most scenarios and the most app interaction.

The app crawl is the priciest single scout at 133k and 26 minutes, because it actually operates the application. It also found two of the six defects, so it tends to earn its keep.

The second cycle is much cheaper

Discovery dedups against the bank and your existing suites, so scouts return only what is genuinely new. Turn 2 implements only the new drafts — usually a handful after a feature, not 45.

Turn 3 runs the whole bank in about 6 minutes of wall clock and almost no tokens: running Playwright is not a model operation.

Spending less

  • Scope it. /tddbanking:discover payments runs the whole cycle against one capability.
  • Skip the crawl if your app is hard to drive or your docs are good — story-driven and defect-driven cost about a third of it between them, and need no running app.
  • Let turn 2 run long rather than wide on a small bank. The parallel fan-out is what makes it fast, not what makes it cheap.

These are numbers from one run against one mid-sized app — 15 capabilities, ~11 routes, 4 roles, an existing Playwright suite. A larger surface costs more, and an app that is awkward to drive costs more again. Treat the shape as reliable and the absolute figures as an order of magnitude.

The bank

One file per capability. The untested parts are visibly marked.

Scenarios live in Gherkin. Drafts — @draft, not yet implemented — and live tests share one .feature file, so a file reads as the complete intent of a capability.

  • Coverage is live ÷ (live + draft), computed from the tags.
  • Promoting a scenario is deleting one tag.
  • Every scenario cites evidence. No evidence, no scenario — a bank containing invented tests stops being trusted, and that is unrecoverable.

Credit

It doesn't invent any of this. It wires together three things that already work.

Each of these is good on its own, and each solves one part of the problem. The plugin's contribution is the handoffs between them, and the discipline to run every step instead of stopping after the interesting one. It invokes them, so they have to be installed — and nothing is vendored, because a copy stops receiving its author's improvements and starts being a fork nobody maintains.

The tdd skill ↗

by Matt Pocock invoked at steps 2 and 5

The red/green discipline, and the reason the tests are worth keeping. It defines what a good test is, where tests belong — seams, the public boundary you observe behaviour at — and the anti-patterns that quietly ruin a suite. tddbanking defers to it rather than restating it.

OpenSpec ↗

Fission AI invoked at steps 4 and 5

Turns a rough requirement into a real specification — proposal, delta specs, design, and a task-by-task implementation plan. Every proven bug leaves the loop as an OpenSpec change, not as a bug report someone has to re-specify.

playwright-bdd ↗

by Vitaliy Potapov the format, at steps 2, 3 and 5

Gherkin feature files compiled into Playwright specs. Thin step definitions, locators in Page Objects. It is what makes a browser test readable as a requirement instead of a script — which matters, because these tests double as the acceptance criteria handed to OpenSpec.

If you already use any of these, this plugin is the sequencing you were going to write yourself.

Two things worth knowing

A green test on the first run is a success, not a failure of TDD.

Your app already exists, so most scenarios document behaviour that already works — that is coverage gained. A red one is a bug you just found.

No turn tells you what to do next within its own scope.

Earlier versions ranked drafts by priority, and the first real run implemented 8 of 58 and felt finished. A shortlist reads as permission to stop. Each turn's contract is now completeness.

Install

Two commands to add it. Two more to start.

1 · Add the plugin, once

/plugin marketplace add DeepSpringAI/tddbanking
/plugin install tddbanking@tddbanking

2 · In the repo of the app you want covered

/tddbanking:init

One-time: playwright-bdd, config, scripts, CI workflow.

/tddbanking:discover

Turn 1 — it tells you what to run next.

What it needs

Node, and a web app you can run locally. Beyond that it depends on the three projects it is built from — it invokes them, so they have to be installed. Turns 1–3 work without any of them; the last two do not.

OpenSpec turns 4 and 5

npm i -g @fission-ai/openspec
openspec init --tools claude

Note what the second command does, because it is easy to miss: openspec init is what creates the openspec-* skills, generating them into that project's .claude/skills/. They are project-scoped, not global — installing the CLI alone gives you no skills, and turns 4 and 5 will report them missing.

The tdd skill turn 5, and improves turn 2

A personal Claude Code skill this plugin does not ship. Get it from mattpocock/skills and put it in ~/.claude/skills/tdd/. Without it the loop still finds and files your bugs; it just stops before fixing them.

webapp-testing is used for app-crawl and for reproducing failures by hand. If it is missing, the crawl drives Playwright directly.

Turn 1 checks all four and tells you what is missing before you start, rather than letting you discover it four turns later.

Keeping up with the skills it borrows from

This plugin paraphrases rules from skills it does not own, and those can go stale silently: a skill that loads perfectly while one of its rules changed underneath is a failure no missing-skill check can catch, because nothing is missing. So the versions it describes are pinned by content hash in upstream-skills.json.

node scripts/check-upstream.mjs

Add --upstream to ask whether the source itself has moved on. Drift is a prompt to re-read, not a fault — and if a rule genuinely changed, the check names the files to update.

! Before the crawl writes anything

It asks you to confirm the target is disposable and its outbound email is sandboxed. Crawling means doing things — submitting forms, cancelling records. Point it at a seeded local instance, never staging.

Commands: init, discover, implement, verify, file, develop, plus read-only status.

Run it again after your next feature, and it picks up from the bank it already built.
